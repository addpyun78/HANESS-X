# T-102 전체 시스템 점검·정리 (원자 단위)

## ★ 무인 실행 모드 (이 섹션이 아래 모든 규칙보다 우선)
사용자는 중간에 확인할 시간이 없다. **사람에게 묻지 말고** 아래 자동 결정 규칙으로 끝까지 진행한다.
실행 방법은 둘 중 하나다.
- **기본: Claude Code 자동(auto) 모드 대화창에 이 티켓을 그대로 맡김.** 한 대화에서 끝까지 이어서 진행한다.
- 선택: `scripts/audit/run-audit.mjs` 러너(사용량 한도 뒤 자동 재개가 필요할 때). 러너는 소단계마다 새 대화로 실행한다.

### 자동 승인 규칙 (D.14가 이 표로 `approved.json`을 만든다)
| 종류 | 자동으로 진행 | 자동으로 보류(기록만) |
| --- | --- | --- |
| 버그 — 치명·높음 | 고칠 때 위험도 낮음·보통 | 위험도 높음 |
| 버그 — 보통·낮음 | 위험도 낮음 | 그 외 |
| 보안 | 전부(같은 큰 버전 안에서 해결될 때) | 큰 버전 변경이 필요한 경우 |
| 껍데기 | 작업량 S이고 원래 티켓 수용 기준이 분명 → **구현** | 그 외 → **숨김**(비활성 + "준비 중이에요") |
| 업데이트 | 보안 수정 + 작은 버전(패치·마이너), 공개 14일 지남 | 큰 버전(메이저) |
| 문서 차이 | 전부 | — |
| 통합 | 옛 구현끼리 동작 차이 0개 + 위험도 낮음 | 동작 차이가 있거나 위험도 보통 이상 |
| 폴더 구조 이동 | — | 전부(제안만 남김) |
| 삭제 | 4근거 모두 해당 + 종류가 의존성·export·파일·추적 중인 생성물 | 그 외 전부 |
| Git 기록 다시 쓰기 | — | 하지 않음 |
| 사용자 데이터(세션·첨부·로그·모델) | — | **절대 삭제 안 함** |
| main에 합치기 | H.3 통과 기준 4개 + 치명 발견 남은 것 0 → `git merge --no-ff` | 하나라도 미달이면 브랜치에 두고 `final.md`에 이유 |
| 원격 저장소(push) | — | **절대 하지 않음** |

### 무인 모드에서 바뀌는 규칙
- 아래 본문의 🖐(사람 확인)·"사용자에게 질문"·"승인 대기"는 전부 이 표의 자동 결정으로 대체한다.
- 시작할 때 이미 실패하는 테스트가 있으면 발견으로 등록하고 계속한다. 단, 이번 작업으로 **새로 실패하는 테스트는 0개**여야 한다.
- 판단이 애매하면 항상 **보류** 쪽을 고른다(아무것도 안 바꾸는 쪽이 안전).
- 소단계 하나가 끝날 때마다 `progress.md` 갱신·커밋. **러너가 시킨 실행이면** 거기서 마치고, **대화창에서 시킨 경우면 멈추지 말고 다음 소단계로 계속** 진행한다.
- 대화가 길어져 앞 내용이 요약(압축)된 뒤에는 반드시 `CLAUDE.md`와 `docs/audit/progress.md`를 다시 읽고 이어간다.
- 사용량 한도에 걸리면 러너가 기다렸다가 이어서 한다. 작업 중 한도 메시지를 받으면 즉시 `progress.md`에 위치를 쓰고 마친다.

## 왜 이 순서인가
- "찾고 고치고 지우기"를 한 번에 하면 AI가 멀쩡한 코드를 안 쓰는 코드로 착각해 지운다.
  HARNESS-X는 플러그인·훅·MCP 도구·CLI 명령을 **파일 이름으로 나중에 불러오기** 때문에 자동 도구가 특히 잘못 판단하기 쉽다.
- 고정 순서: **A 안전망 → B 기능 지도 → C 진단(읽기만) → D 보고서·사람 승인 → E 고치기 → F 통합 → G 삭제 → H 최종 비교·재발 방지.**
- "기능이 사라지지 않았다" = B 기능 지도의 모든 기능이 정리 전후로 똑같이 통과 + A 단계 목록 스냅샷(플러그인·도구·명령·설정·화면 동작·API·훅)이 G 단계 뒤에도 같음.

## 작업 규칙 (이 티켓 전용, CLAUDE.md에 복사)
1. 브랜치 `audit/2026-11`에서만 작업. 태그 `pre-audit`이 되돌릴 지점.
2. 원자 항목 = 동사 1개 · 결과물 1개 · 검증 1개. 항목 하나 = 커밋 하나 (`T-102/<항목>: 요약`). 측정만 하는 항목은 결과 파일 커밋.
3. **A·B 단계:** 측정 스크립트(`scripts/audit/`), 결과(`docs/audit/`), 테스트 추가, 테스트 도구 devDependency 추가만 허용. 제품 코드(`packages/*/src`, `apps/*/src`) 수정 금지.
4. **C·D 단계:** `docs/audit/`, `scripts/audit/` 외 변경 금지(C.0 가드가 검사). 외부 도구는 `pnpm dlx`로 실행해 package.json을 바꾸지 않는다.
5. **E·F·G 단계:** `docs/audit/approved.json`에 있는 항목만. 발견 1건씩 처리.
6. 커밋마다 "검증 묶음" 실행: `pnpm -r build` → `pnpm test` → `pnpm test:features`(B 이후). 단계 마감 때는 + E2E + 전부 눌러 보기 + 엔진 스모크.
7. 검증 묶음 실패 → 그 커밋 `git revert`, `findings.json`의 해당 발견을 `보류: <이유>`로 기록하고 다음 항목으로.
8. 하위 항목이 실행 중에 정해지는 곳(목록 개수만큼 반복)은 티켓 맨 아래 "실행 중 추가 항목" 섹션에 원자 항목으로 추가한 뒤 하나씩 처리.
9. 소단계 하나가 끝나면 결과를 `docs/audit/progress.md`에 남긴다(러너 실행이면 거기서 마치고, 대화창 실행이면 계속).
10. 사용자에게 보이는 요약은 쉬운 말(T-100 쉬운 말 검사기 통과).
11. 이 기간 새 기능 추가 금지.
